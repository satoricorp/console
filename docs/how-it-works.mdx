GX adds a context layer around your existing Git workflow. It captures what happened during coding sessions, attaches that context to reviewable revisions, and publishes normal Git branches and commits — so reviewers see the intent behind a change, not just the final diff.

## The problem

Git was built for humans typing commits one at a time. A commit stores a snapshot and a short message, and for human-paced work that is usually enough.

Agent-written code breaks two of Git's assumptions:

1. **The context that explains a change never makes it into the repo.** The prompt that asked for the change, the commands the agent ran, the tests it executed, the dead ends it backed out of — all of that lives in a session transcript that is gone by review time. The commit message is whatever one line survived.
2. **Review is now the bottleneck.** The cost of generating code is dropping toward zero, but teams still review line by line. When a pull request is one large undifferentiated diff with a thin message, the reviewer has to reconstruct intent from scratch.

## What GX captures

GX records work at three levels:

- **Sessions** — transcripts from coding agents (for example, Claude Code transcripts via `Stop`/`SessionEnd` hooks that `gx init` installs). Sessions are retained locally for 30 days and published alongside the code they produced.
- **Revisions** — each `gx commit` records the staged changes as one reviewable unit, down to individual [hunks](https://git-scm.com/book/en/v2/Git-Tools-Interactive-Staging) (a few changed lines, not whole files). GX links each revision to the session that produced it — automatically when it can match one, or explicitly when an agent declares it.
- **Agent self-reports** — through the [MCP tools](/docs/mcp), an agent can attach a task summary and the commands and tests it ran directly to the revision it is committing.

Because changes are stored as described hunks with linked sessions, GX can point reviewers at the parts that matter and let them skim the mechanical rest — instead of forcing a line-by-line read of everything.

## Stacks and revisions

You are likely used to the Git mental model of branches and commits. These work great until you need to edit a commit, rebase, or reorder work — then the tooling gets sharp.

- A **revision** is analogous to a commit, but it can be edited and updated after it is recorded. Revisions are JJ-backed, so amending one never requires an interactive rebase.
- A **stack** is analogous to a branch, but with metadata: an ordered line of revisions, their base, publish state, and remote sync status. Status output also calls a stack a **feature**.

Here is a stack as `gx status` shows it — two revisions built on `main`, not yet published:

```text
› ● retry-backoff  s1 · feature/retry-backoff · main · draft · ↑2
        ↑ zlsrnuk  add jitter to backoff delays  latest
        ↑ qlmmuyy  add exponential backoff helper
```

Each revision is separately reviewable, and the order tells the story of the work. Stacks also make stacked PRs natural: each stack exports to a branch, and dependent work stays in sequence instead of piling into one giant diff.

## Everything still exports to Git

GX maintains revisions and stacks locally. When you push — via `git push` with the GX pre-push hook, or `gx push` — GX publishes:

- normal Git **branches and commits**, so your Git log and GitHub stay standard;
- the linked **sessions and metadata** to GX Cloud as a review bundle.

Nothing about your repository becomes GX-specific. If you stopped using GX tomorrow, your branches and commits remain ordinary Git.

## Replace your git workflow

Instead of manually creating a branch and commit:

```bash
git checkout -b feature/my-change
git add .
git commit -m "update stuff"
git push
```

Start with:

```bash
git add <files>
gx commit -m "describe this revision"   # add -b feature/my-change for a new branch
gx status                               # alias: gxs
git push                                # or gx push
```

`gx commit` records staged work as a GX revision. `gx status` shows local stacks and remote state. `git push` (with the GX pre-push hook) or `gx push` publishes code plus session data and metadata to GitHub and GX Cloud.

For a large messy working copy, agents can still run `gx generate` to bulk-organize changes into smaller revisions, then inspect with `gx status` and push when ready.

## Where the context goes

The published review bundle powers the review surfaces:

- [PR Summaries](/docs/github) tell reviewers what changed, why, and which files deserve attention first.
- [`@gx` chat](/docs/github) answers questions inside the pull request, citing the sessions and diffs it used.
- [`gx review`](/docs/cli) runs a local review using the same captured context before you ever open a PR.

The recommended way to use GX with agents is through the [MCP server](/docs/mcp). That lets your coding tool record and publish work without touching the terminal.
