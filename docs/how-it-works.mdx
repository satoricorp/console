---
title: How it works
description: What GX captures, what revisions are, and how everything stays normal Git.
---

GX adds a context layer around your existing Git workflow. It captures what happened during coding sessions, attaches that context to reviewable revisions, and publishes normal Git branches and commits — so reviewers see the intent behind a change, not just the final diff.

## The problem

Git was built for humans typing commits one at a time. A commit stores a snapshot and a short message, and for human-paced work that is usually enough.

Agent-written code breaks two of Git's assumptions:

1. **The context that explains a change never makes it into the repo.** The prompt that asked for the change, the commands the agent ran, the tests it executed, the dead ends it backed out of — all of that lives in a session transcript that is gone by review time. The commit message is whatever one line survived.
2. **Review is now the bottleneck.** The cost of generating code is dropping toward zero, but teams still review line by line. When a pull request is one large undifferentiated diff with a thin message, the reviewer has to reconstruct intent from scratch.

## What GX captures

GX records work at two levels:

- **Sessions** — transcripts from coding agents (for example, Claude Code transcripts via `Stop`/`SessionEnd` hooks that `gx init` installs). GX stages a lightweight reference locally, and on `git push` publishes the session alongside the code it produced; the published session is kept with your review history in GX Cloud.
- **Revisions** — each plain `git commit` records the staged changes as one reviewable unit via the GX hooks, down to individual [hunks](https://git-scm.com/book/en/v2/Git-Tools-Interactive-Staging) (a few changed lines, not whole files). GX links each revision to the session that produced it automatically, by matching the changed hunks against captured session activity — you never attach anything by hand.

Because changes are stored as described hunks with linked sessions, GX can point reviewers at the parts that matter and let them skim the mechanical rest — instead of forcing a line-by-line read of everything.

## Revisions

You already know the Git mental model of branches and commits. GX keeps exactly that model and records review context around it — no new objects to learn.

A **revision** is a Git commit plus the review context GX records around it: the session that produced it, the changed hunks, and a generated summary. Your branch is just a Git branch; GX adds nothing on top of it. Each revision is separately reviewable, and the order of commits on the branch tells the story of the work.

## Everything is still just Git

When you `git push`, the GX pre-push hook publishes:

- normal Git **branches and commits**, so your Git log and GitHub stay standard;
- the linked **sessions and metadata** to GX Cloud as a review bundle.

Nothing about your repository becomes GX-specific. If you stopped using GX tomorrow, your branches and commits remain ordinary Git.

## Your Git workflow, unchanged

You might expect a set of `gx` verbs to learn. There are none for everyday work — after `gx init`, keep using the Git you already know:

```bash
git switch -c feature/my-change        # a normal branch, when you want one
git add <files>                        # choose the scope of the change
git commit -m "describe this change"   # a hook records it as a GX revision
git push                               # the pre-push hook captures sessions + publishes
```

Plain `git commit` records the staged work as a GX revision. Use `git status` to inspect local state and `gx review` (alias `gxr`) to review the current change. Plain `git push` publishes the code plus linked session data and metadata to GitHub and GX Cloud through the pre-push hook.

## Where the context goes

The published review bundle powers the review surfaces:

- [PR Summaries](/docs/github) tell reviewers what changed, why, and which files deserve attention first.
- [`@gx` chat](/docs/github) answers questions inside the pull request, citing the sessions and diffs it used.
- [`gx review`](/docs/cli) runs a local review using the same captured context before you ever open a PR.

The recommended way to give agents review context is through the [MCP server](/docs/mcp): it exposes the `gx_review` tool so your coding tool can review its own work in the loop, without dropping to the terminal.
