GX helps teams understand and review AI-written code without treating every pull request as an isolated diff.

The open-source `gx` CLI installs Git hooks that capture coding sessions and link them to your commits as reviewable revisions, and adds AI review with `gx review`. You keep using plain Git — `git add`, `git commit`, `git push` — and GX does its work automatically on the way through. The paid GitHub features add [PR Summaries and `@gx` chat](/docs/github) inside GitHub pull requests.

## Core workflow

You keep working in plain Git. Once `gx init` installs the hooks, your normal `git` commands do the GX work automatically — there is no GX-specific save verb to learn.

```bash
git add <files>                        # choose the scope of the change
git commit -m "describe this change"   # a hook records it as a GX revision
git push                               # the pre-push hook captures sessions + publishes review context
```

A commit looks like any other:

```text
$ git add src/retry.js
$ git commit -m "add retry helper with attempt limit"
[main b694d3be] add retry helper with attempt limit
 1 file changed, 12 insertions(+)
```

Behind that ordinary commit, GX's `prepare-commit-msg` and `post-commit` hooks record a GX **revision** (`qltmnmynnyzk`) — an editable review unit that carries review context: which captured session produced it, and where it sits among your branches. When you `git push`, the pre-push hook links each captured session to the hunks it changed and publishes the review bundle.

GX adds three commands on top of Git — and nothing that duplicates Git itself:

```bash
gx init      # set up hooks and identity in a repo (run once)
gx review    # AI review of your current change, with codebase + session context (alias: gxr)
gx doctor    # check capture, hooks, and workflow state
```

## Product model

GX uses a few terms consistently:

- **Session**: captured coding context from an agent, editor, or shell.
- **Revision**: one reviewable logical change — a Git commit plus the context that explains how it was produced.
- **Stack**: an ordinary Git branch carrying more than one revision — a line of work reviewed together.
- **Review bundle**: the published payload that joins code changes, sessions, metadata, and review evidence.

These are just names for what your ordinary Git commits and branches already are, plus the review context GX records around them. You never leave Git to get them.

A Git commit is a durable snapshot plus a short message. That is still useful, but it is often too thin for AI-generated work: the commit does not know which agent session produced it, which prompt or shell commands mattered, whether the change was split out of a larger messy workspace, or how it relates to nearby generated work.

A GX revision is the review unit: a Git commit plus the review context recorded around it — session provenance, generated summary, file-level intent, and its position on the branch. Calling it a revision keeps the focus on reviewable evolution of the work, not only on the final Git object.

Your branch stays a plain Git branch. GX records the ordered revisions and context around the branch you already have, so reviewers can see the sequence of intent instead of only the final branch state.
