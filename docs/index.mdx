GX helps teams understand and review AI-written code without treating every pull request as an isolated diff.

The open-source `gx` CLI captures coding sessions, records staged changes as reviewable revisions inside stacks, and publishes those stacks as normal Git branches and commits. The paid GitHub features add [PR Summaries and `@gx` chat](/docs/github) inside GitHub pull requests.

## Core workflow

GX keeps the Git staging mental model: `git add` chooses the scope, and `gx commit` replaces `git commit`.

```bash
git add <files>                        # choose the scope of the revision
gx commit -m "describe this revision"  # record it as a GX revision
gx status                              # inspect stacks before publishing (alias: gxs)
git push                               # the GX pre-push hook publishes sessions + metadata
```

A first commit looks like this:

```text
$ git add src/retry.js
$ gx commit -m "add retry helper with attempt limit"

Revision recorded
Message       add retry helper with attempt limit
Revision      qltmnmynnyzk
Commit        b694d3be
Stack         main
Provenance    absent
```

Every `gx commit` produces a normal Git commit (`b694d3be` above) plus a GX **revision** (`qltmnmynnyzk`) that stays editable and carries review context: which captured session produced it, what the agent reported doing, and where it sits in its stack. `Provenance` shows whether a captured coding session was linked to the revision — `absent` here because no agent session was running.

The CLI installer also adds two shortcuts:

```bash
gxs   # gx status
gxr   # gx review
```

For a large messy working copy, the advanced bulk organizer can split the work into smaller revisions automatically:

```bash
gx generate   # hidden from gx --help; see CLI → Bulk organize
gx status
gx push
```

## Product model

GX uses a few terms consistently:

- **Session**: captured coding context from an agent, editor, or shell.
- **Revision**: one reviewable logical change, including the code diff and the context that explains how it was produced.
- **Stack** (also called a **feature** in status output): an ordered line of revisions that should be reviewed together.
- **Review bundle**: the published payload that joins code changes, sessions, metadata, and review evidence.

GX still outputs normal Git branches, commits, and pull requests. The GX terms describe the product model before it is exported to Git.

A Git commit is a durable snapshot plus a short message. That is still useful, but it is often too thin for AI-generated work: the commit does not know which agent session produced it, which prompt or shell commands mattered, whether the change was split out of a larger messy workspace, or how it relates to nearby generated work.

A GX revision is the review unit. It can become a Git commit, but it carries richer review context around that commit: session provenance, generated summary, file-level intent, and its position in the stack. Calling it a revision keeps the focus on reviewable evolution of the work, not only on the final Git object.

A Git branch is a pointer in a repository. A GX stack is the product shape of the work: ordered revisions, their dependencies, and the context needed to understand them. GX exports stacks to branches because GitHub and Git still expect branches, but agents and reviewers work better with stacks because they can see the sequence of intent instead of only the final branch state.
