Start with GX when you want coding agents to produce reviewable work instead of one large undifferentiated diff.

The usual path is:

1. Install GX.
2. Sign in with GitHub.
3. Initialize GX in a repository.
4. Generate, inspect, and push a stack.

## Install

> Windows is not supported yet.

### macOS

Install the [Mac app](/download) if you want the menu-bar app to manage local setup for you. The app installs or updates the CLI, installs the `gxg`, `gxs`, and `gxr` shortcuts, and shows local setup status.

### Linux

Install the CLI directly:

```bash
curl -fsSL https://download.gx.run/install.sh | sh
```

After installation, verify that `gx` is on your path:

```bash
gx version
```

The CLI installer places `gx`, `gxg`, `gxs`, and `gxr` in `~/.local/bin`.

## Sign in

GX uses GitHub for identity.

```bash
gx auth login
gx auth status
```

The web app sign-in and CLI sign-in are linked through your GitHub account. After signing in from the CLI, you can see signed-in CLI devices in the web app, including machine name, GX version, last-used time, and session expiry.

## Initialize a repo

Run `gx init` from the repository you want GX to manage.

```bash
gx init
```

Initialization prepares GX in the repo, configures local identity, and sets up capture support for coding-session provenance.

## Set API Keys

The open-source CLI can use model credentials to infer stacks and revisions:

```bash
export OPENAI_API_KEY="..."
export ANTHROPIC_API_KEY="..."
```

Set one or both keys before running `gxg` or `gx generate` if you want local stack and revision inference. This path is for the CLI and MCP workflow. Paid pull request features use GX Cloud.

## First stack

After making changes:

```bash
gx generate # gxg
gx status   # gxs
gx push
```

`gxg` looks at the current repo state and the captured coding-session context. It groups the work into reviewable revisions, orders those revisions into one or more stacks, and writes that structure locally.

`gxs` shows what GX found: unstaged files, local stacks, revisions, base branches, and remote state. Use this before pushing so you can catch the wrong split, an unexpected file, or remote divergence early.

`gx push` exports the stack back into Git and GX Cloud. The Git output is normal branches and commits, so GitHub can open pull requests. The GX metadata adds the richer context: revision order, session provenance, summaries, and the review bundle that powers PR features.

## Agent workflow

For simplicity, use the MCP tools and avoid asking agents to run the CLI directly. The MCP is built to support this flow:

```bash
gx sync     # Pulls changes from remote
gx generate # Uses AI to generate organized and semantic commits and branches
gx status   # Checks the status of gx generate and shows any unstaged files
gx push     # Pushes all new stacks to remote and repairs incomplete previous pushes
```

The MCP server runs through the local CLI, so agents use the same GX workflow a human would use from the terminal.
