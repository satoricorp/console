title: Interact with GX in GitHub PRs
description: Use paid GX Cloud features to generate PR Summaries and chat with @gx inside GitHub pull requests.
---

GX adds paid review features inside GitHub pull requests.

The CLI can generate and publish stacks locally. GitHub PR Summaries and `@gx` chat run through GX Cloud and require the paid PR feature set (or an active free trial).

## Prerequisites

1. Sign in with `gx auth login`.
2. Install the GX GitHub App on the repository so GX can post comments and read PR context.
3. Point the GitHub App webhook at the GX Cloud API:

```text
https://api.gx.run/github/webhook
```

4. Publish work through GX (`gx push`, or `git push` with the GX pre-push hook). A PR created only in the GitHub UI will not get a GX summary until that branch is pushed through GX with capture metadata present.

## PR Summaries

GX can post a PR Summary comment on a GitHub pull request.

The summary is intentionally short. It should tell reviewers:

- what changed
- why it changed
- which files deserve attention first
- which files are mechanical or safe to skim
- what session or agent context is relevant

The goal is to point reviewers to the important parts of the change instead of forcing them to read every line with no context.

### When summaries are generated

GX posts summaries from these paths:

- **GitHub webhook** — on `pull_request` `opened` / `synchronize`, when the bookmark already has a published GX event
- **After publish** — when `gx push` (or the publish hook path) has a PR number and the GitHub App is installed

`POST /v1/summaries/generate` stores a summary in GX Cloud. It does **not** post the comment to GitHub by itself.

### Trial and paid access

Orgs on the free plan get PR Summaries during a free trial window (default 7 days from org creation, or the entitlement returned by GX Cloud). After the trial ends, summaries require a paid plan. When quota blocks a summary, GX can post an upgrade comment on the PR instead.

## Chat with `@gx`

Mention `@gx` in a PR comment to ask questions about the pull request.

Ask for orientation:

```text
@gx summarize this PR for someone reviewing it cold
@gx which files should I review first?
@gx what is safe to skim?
```

Ask about a specific part of the diff:

```text
@gx explain the auth callback changes
@gx why did the migration file change?
@gx what does this new background job do?
```

Ask for risk or follow-up review:

```text
@gx what is the highest-risk change in this PR?
@gx are there missing tests?
@gx is this related to the previous retry bug?
```

GX answers from available review sources and cites the sources it used.

### Override learned rules

You can use `@gx` to retire a learned rule:

```text
@gx skip rule never use var
@gx do not enforce this migration naming rule
```

When a matching active rule exists, GX retires it and records the override. Rule overrides require GitHub **write**, **maintain**, or **admin** permission on the repository. Collaborators without write access are denied.

## Data sources

GX answers from the current PR first: the published GX revision diffs, changed hunks, file paths, PR comments, and the latest PR Summary.

When available, GX can also use captured coding-session context, indexed codebase context, previous findings, learned rules, and git blame history. Current PR changes remain the source of truth for what changed.

## GitHub App

To post summaries and replies, GX needs installation-scoped access for the repository. The local CLI can still generate and push branches without the paid PR feature set. The paid features are the GitHub-hosted review layer: PR Summaries, `@gx` chat, and cloud-backed review context.
